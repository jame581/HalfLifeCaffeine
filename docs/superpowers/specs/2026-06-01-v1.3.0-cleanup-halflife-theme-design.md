# HalfLife Caffeine v1.3.0 — Cleanup, Configurable Half-Life, Theme

**Status:** Approved design (2026-06-01)

**Goal:** Ship v1.3.0 as a focused maintenance-plus-features release: remove the
`lastSyncTime` dead code carried since v1.2.0, let users tune the caffeine
half-life to their own metabolism, and let users pick a background theme so the
widget looks good on non-OLED (MIP / transflective) displays where the navy
palette renders washed-out.

**Non-goals (researched and explicitly rejected for this release):**

- **Standalone companion app** (Connect IQ Mobile SDK, Android/iOS). User does
  not want a second app to build, sign, and publish.
- **Caffeine as a native Garmin Connect health metric.** Researched: there is no
  supported path. The Health/Connect API only pulls data *out* of Garmin (and
  requires partner-program approval); `FitContributor` can render custom graphs
  but only inside a recorded **Activity** session — wrong semantics for a passive
  all-day tracker, and only after store publication. The existing Connect IQ
  settings page remains the only viable companion surface. A future data-field
  variant (caffeine logged *during* a workout) is the one place "data in Connect"
  is real, but it is a separate product and out of scope here.

---

## Context

The app runs in two processes that share no in-memory state (see CLAUDE.md):

1. **Glance process** — only `(:glance)`-tagged code is linked. `GlanceView`
   instantiates `StorageManager` + `CaffeineModel` fresh and reads doses from
   storage directly.
2. **Full-view process** — `HalfLifeCaffeineApp.initializeManagers()` wires up
   the five managers lazily on first `getInitialView()`.

Both processes must honour the new half-life and theme settings, so each feature
has to be applied in *both* the glance path and the full-view path.

Settings flow through `Application.Properties` (typed, defined in
`resources/properties.xml` + `resources/settings.xml`, mirrorable from the phone
companion). The two new settings follow this same convention.

## Section 1 — Dead-code cleanup

The v1.2.0 sync rewrite replaced the incremental `syncToPhone`/`lastSyncTime`
flow with `syncDayToPhone` (full-day replace-day resync). The old persistence
accessors were left in place for one release as a safety net. They have no
callers in `source/` and are removed now.

**Changes:**

- **`source/StorageManager.mc`:** remove `saveLastSyncTime()`, `getLastSyncTime()`,
  `getDosesSince()`, and the `LAST_SYNC_KEY` private constant.
- **`source/SyncManager.mc`:** `initialize(storageManager)` currently takes a
  parameter it discards ("kept for API compatibility"). Change to a no-arg
  `initialize()`.
- **`source/HalfLifeCaffeineApp.mc`:** update the one call site in
  `initializeManagers()` from `new SyncManager(storageManager)` to
  `new SyncManager()`.

**Verification:** grep `getLastSyncTime`, `saveLastSyncTime`, `getDosesSince`,
`LAST_SYNC_KEY` across `source/` — expect zero matches after the change. No
behaviour change; the existing test suite must still pass.

**Follow-up note (NOT in scope):** `SyncManager.handlePhoneMessage` does not
handle the `presets` field, although CLAUDE.md's protocol section says it should.
This is pre-existing drift, unrelated to v1.3.0. Track separately; do not fix
here to keep the release focused.

## Section 2 — Configurable half-life

Caffeine half-life varies materially between people (~3–7h typical; shifted by
smoking, genetics, pregnancy, oral contraceptives, liver function). The app is
literally named after the half-life, so personalizing it is on-brand.

### Design principle: keep `CaffeineModel` pure

`CaffeineModel` is currently a pure domain class with no dependency on
`Application.Properties` — this is what makes its unit tests trivial. The design
preserves that: the model exposes a setter, and the *callers* read the property
and push the value in. The model never reads `Application.Properties`.

### Model changes (`source/CaffeineModel.mc`)

- Replace `private const HALF_LIFE_SECONDS = 20520;` with a mutable instance var
  `private var _halfLifeSeconds;` initialized to `20520` in `initialize()`
  (preserves the 5.7h default and keeps every existing test green with no setter
  call).
- Add `function setHalfLifeSeconds(seconds)` — assigns `_halfLifeSeconds`
  (guard: ignore null / non-positive).
- `decayedAmount` uses `_halfLifeSeconds` instead of the constant. No other math
  changes — projections, `getMinutesToSafe`, and pruning all route through
  `decayedAmount` / `getCurrentLevel`, so they inherit the new half-life
  automatically.

### Property plumbing

- **New property** (`resources/properties.xml`): `halfLifeHours`, type `float`,
  default `5.7`.
- **New setting** (`resources/settings.xml`): numeric, title
  "Caffeine half-life (hours)", `min="3"` `max="10"`.
- **New helper** `Util.getHalfLifeSeconds()` (`Util` is already `(:glance)`):
  reads `halfLifeHours`, defaults to `5.7` if null/invalid, clamps to
  `[3.0, 10.0]`, returns `hours * 3600` as a Number. Centralizes the
  default-and-clamp logic so glance and full-view stay consistent.

### Wiring (both processes)

- **`HalfLifeCaffeineApp.initializeManagers()`:** after constructing the model,
  call `caffeineModel.setHalfLifeSeconds(Util.getHalfLifeSeconds())`.
- **`GlanceView.onUpdate()`:** after `new CaffeineModel()`, call
  `model.setHalfLifeSeconds(Util.getHalfLifeSeconds())` before any level math.
- **`HalfLifeCaffeineApp.onSettingsChanged()`:** re-apply
  `caffeineModel.setHalfLifeSeconds(Util.getHalfLifeSeconds())` so a half-life
  change from the phone or settings menu takes effect live, then
  `requestUpdate()`.

### Companion parity

- **`SyncManager.handlePhoneMessage`:** in the `settings` branch, if the message
  carries `halfLifeHours`, write it to the `halfLifeHours` property. (After this,
  the existing `onSettingsChanged` re-apply path picks it up.)
- **`companion/settings/index.html`:** add a half-life numeric input to the
  settings form; include `halfLifeHours` in the settings payload sent to the
  watch. Ships from `main` (gh-pages is deprecated — see project notes).

### Tests (`test/CaffeineModelTest.mc`)

- `testDefaultHalfLifeIs20520Equivalent` — a dose of 100mg is ~50mg after
  20520s with no setter call (locks the default).
- `testSetHalfLifeSecondsChangesDecay` — `setHalfLifeSeconds(3*3600)`, dose
  100mg, assert ~50mg after 3h and ~25mg after 6h (within a small epsilon).
- `testSetHalfLifeSecondsIgnoresInvalid` — `setHalfLifeSeconds(0)` and
  `setHalfLifeSeconds(null)` leave decay unchanged.

## Section 3 — Theme / background color

**Problem:** the navy background (`0x1A2332`) and navy-derived structural colors
look washed-out / low-contrast on MIP (memory-in-pixel / transflective) displays
such as fenix 6/7 base models and fr955. Users have requested a true-black
background. Black also benefits AMOLED devices (battery + contrast).

### Design principle: `const` → `var`, zero call-site churn

`Colors` is a `(:glance)` module. The three theme-dependent colors become
mutable module vars set by an `applyTheme()` function. Because they keep the same
names (`Colors.BG`, `Colors.TRACK`, `Colors.AXIS`), **every existing call site is
untouched** — they simply read the current value. Module vars are per-process
singletons, which is exactly right: each process applies the theme once and all
its views read the same values.

### `source/Colors.mc` changes

- Change `BG`, `TRACK`, `AXIS` from `const` to `var` (defaults = current Navy
  values, so behaviour is unchanged until a theme is applied).
- Keep `ACCENT`, `TEXT_PRIMARY`, `TEXT_SECONDARY`, `TEXT_DIM`, `WARNING`,
  `DANGER`, `BEDTIME` as `const` — they read acceptably on both backgrounds.
- Add `function applyTheme()`:
  - Reads the `theme` number property (default `0` if null/invalid).
  - **Navy (0):** BG `0x1A2332`, TRACK `0x2A3548`, AXIS `0x3D4A60`.
  - **Black (1):** BG `0x000000`, TRACK `0x1C1C1C`, AXIS `0x333333`.

### Property plumbing

- **New property** (`resources/properties.xml`): `theme`, type `number`,
  default `0`.
- **New setting** (`resources/settings.xml`): `list` settingConfig with two
  `listEntry` options — `0` → "Navy (default)", `1` → "Black". Titles via new
  Strings resources (e.g. `@Strings.SettingThemeTitle`, `@Strings.ThemeNavy`,
  `@Strings.ThemeBlack`).

### Wiring (both processes)

- **`GlanceView.onUpdate()`:** call `Colors.applyTheme()` at the top, before any
  drawing.
- **`HalfLifeCaffeineApp.initializeManagers()`:** call `Colors.applyTheme()`
  (applies before the first `SummaryView` draws).
- **`HalfLifeCaffeineApp.onSettingsChanged()`:** call `Colors.applyTheme()` then
  `requestUpdate()` so a theme switch is immediate.

### Why a curated 2-theme list, not a color picker

An arbitrary background color would break the contrast contract with the fixed
text/accent colors (e.g. white text on a light background = invisible). Navy +
Black satisfies the actual request (true black for MIP) with zero contrast risk.
A third theme can be added later by extending `applyTheme()` and the list — no
structural change.

## Section 4 — Testing & rollout

### Automated

- Run the full `(:test)` suite (existing + new half-life tests) via VS Code
  "Run Tests" on `vivoactive5_sim`. All must pass.

### Manual / visual (theme cannot be unit-tested)

Test the matrix on at least two devices spanning both display technologies:

- **MIP:** `fenix7` (or `fr955`) — verify Black theme noticeably improves
  contrast vs Navy; verify Navy still renders as before.
- **AMOLED:** `vivoactive5` — verify both themes render correctly, no clipping in
  the round safe area.

For each device × theme, walk all four views (Summary, Timeline, Log, History) +
DayDetail + the glance tile, confirming no unreadable text and no leftover navy
artifacts in the Black theme (the TRACK/AXIS swap is the thing to watch).

Also verify: changing half-life in the simulator settings updates the projected
levels and "safe in" times live (via `onSettingsChanged`).

### Release

- Bump version to `1.3.0` (`manifest.xml` / wherever the store version lives).
- Multi-device release build:
  `monkeyc -e -f monkey.jungle -y D:/Garmin/Key/developer_key -o bin/HalfLifeCaffeine.iq`
- Upload to the Connect IQ developer portal with "What's New" copy covering
  configurable half-life and the new theme setting.
- Deploy the updated `companion/settings/index.html` from `main`.
- Tag `v1.3.0` after store approval and a real-device smoke test.

### Docs

- **CLAUDE.md:** document the two new properties; note that `Colors` BG/TRACK/AXIS
  are now runtime-themed via `Colors.applyTheme()`; note `CaffeineModel`'s
  half-life is injected via `setHalfLifeSeconds` (model stays pure). Remove the
  stale mention of `lastSyncTime` accessors if present.
- **README / store listing:** mention configurable half-life and theme.

## Build sequence (informs the implementation plan)

1. **Cleanup** (Section 1) — isolated, independently testable, lowest risk.
2. **Half-life model + tests** (Section 2 model layer) — pure, TDD.
3. **Half-life property + wiring + companion** (Section 2 remainder).
4. **Theme** (Section 3) — `Colors` refactor + property + wiring.
5. **Manual matrix test, version bump, release** (Section 4).

Sections 2 and 3 are independent and could be built in either order; cleanup
goes first because it is the simplest and de-risks the diff.
